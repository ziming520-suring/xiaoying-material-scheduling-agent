# 需求与范围

用户要求先完成三项基础能力，再写具体业务：统一校验、统一重放、统一时间推进。第一阶段已完成这些基础；第三阶段已增加本地业务工具、离线循环和百炼真实模型接入，完整 GitHub 提交仍未完成。

用户已确认 Python、CLI、本地 SQLite；所有写操作格式校验成功前不得改状态。已成功请求同键同参重放原结果，同键异参冲突。状态与成功响应原子保存，支持并发和重启。时间显式初始化，秒精度 UTC，禁止倒退；相同时间不再结算。

校验允许只读状态和诊断日志。确定失败不得留下已提交业务变更；提交结果无法核实时明确 unknown。业务前置条件检查位于重放之后，旧成功请求不因时间变化而重新被拒绝。

当前没有业务到期规则。测试可以注入到期对象证明集中结算与回滚，但不能将该测试对象当作素材或发布任务。

成功标准：规则文档 B01–B16 均有可执行测试证据；CLI 可复制运行；错误可识别，非法输入不崩溃；明确区分基础验证与真实模型效果。

第二阶段已完成业务设计及资料准备，见下文；第三阶段实现了规则检查、时段查询、用户确认、草稿保存和可插拔模型循环，已执行本地工具、离线 Mock 和百炼真实模型验证；真实运行及失败改进记录见 03-evaluation.md。

## 第二阶段：业务需求与成功标准

用户是内容团队，目标是找出待处理素材，形成无冲突、可确认的发布草稿。范围限定单账号和固定时段；输入为素材 ID、合成元数据、每项不可擅改的精确时间、已有排期和测试审核规则。交付每项审核状态、全部风险原因、建议时段、待确认项、真实保存状态及未完成原因。

用户已批准的规则：原时段无风险且可用时直接保存并占位；替代时段或提示风险先保存待确认稿且不占位；阻断风险不可豁免，资料不足必须补查或请求补充；用户确认绑定版本、时段和风险。批量成功项保留；同任务同素材唯一；不接真实发布、不新增草稿到期。

本阶段成功标准：字段与四类工具、独立确认入口有明确契约；六项题面必验均有合成输入与预期；正常、冲突、确认、重复、失败路径能按契约推演；场景资料静态核查通过。详见 [业务契约](06-business-contract.md)、[验收映射](07-acceptance-map.md)、[资料目录](../data/README.md)。

完整项目成功仍要求真实模型根据工具观察改变动作、至少两条动态路径、至少三组真实输入/输出/Trace 覆盖全部六项、执行上限以及 GitHub 提交信息。第二阶段的预期场景和基础测试均不能替代这些要求。
