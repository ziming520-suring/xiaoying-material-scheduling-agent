# 基础方案

本节记录第一阶段基础层；文末第二阶段部分是设计基线，第三阶段实现状态另行补充。

统一请求是 `schema_version`（整数 1）、`request_id`、`operation`、`payload`。操作只有 `system.initialize(initial_time)` 和 `clock.advance(target_time)`。未知字段、重复 JSON 键、非法枚举与时间均拒绝。

统一结果包含 `schema_version`、`request_id`、`operation`、`status`、`data`、`error`。status 为 succeeded / failed / unknown。错误包含 code / message / field / retryable。成功重放返回原结果，不新增会变化的 replayed 字段；是否命中重放写在独立诊断事件中。

## 执行顺序

1. 纯校验与时间归一化，不打开数据库。
2. `BEGIN IMMEDIATE` 取得写事务；SQLite 最多等锁 5 秒。
3. 检查完整 schema，再查 `(operation, request_id)`。规范化请求一致则返回旧结果，不一致则冲突。
4. 新请求进行只读前置条件校验。
5. 执行初始化或时间推进；时间推进调用统一 settle_due，生产处理器列表为空。
6. 同事务写入成功结果，提交后才返回成功。
7. 普通错误回滚；提交异常使用新连接核对重放结果，无法查证则返回 unknown。

参数身份使用 UTC 化、对象键排序、紧凑 UTF-8 JSON 的 SHA-256，并保存规范化文本核对。request_id 不包含在参数摘要中，作为组合键使用。重放记录没有 TTL。

数据库表为 runtime_meta、logical_clock、replay_results。测试到期对象在 tests 中创建，不出现在生产数据库中。已有不兼容、部分初始化或损坏数据库不会自动覆盖。

存储也是校验边界：读取历史响应时检查精确字段、类型、UTC 时间和请求一致性，损坏记录不能作为成功返回。版本 1 只接受当前三张基础表的定义（忽略空白和大小写），不自动迁移手工重建的其他布局；INSERT 显式列出字段，防止位置错配。

## 技术取舍

Python 标准库和 SQLite 满足本地 CLI 的持久化与事务需求，避免引入生产 Runtime 或数据库服务。当前为同机串行写入，不提供分布式锁、网络发布、任意外部工具回滚保证。

ReadOnlyTransaction 只向前置条件检查提供 clock 读取方法；Transaction 提供同事务 SQL 执行但没有 commit 接口。内部处理器是可信项目代码，不是沙箱；不允许远程模型直接提供 SQL 或注册处理器。

本阶段是确定性的工程基础，不实现 ReAct。后续模型循环应位于数据库写事务之外；它可以调用业务工具，但每个有副作用的工具仍须走统一写入口。

## 第二阶段：业务方案（契约，未实现）

用户创建任务 → 模型选择读取、检查、查询、保存中的动作 → 工具执行并返回可信观察 → 模型决定补查、替代建议、等待确认或停止。执行骨架可以预设，但不能用固定条件日志冒充模型决策。模型上限与适配器在第三阶段确定。

| 决定 | 负责方 |
|---|---|
| 是否补查、选择哪一可用替代时段、请求补充或停止 | 模型依据实际工具观察作出决定 |
| 字段有效性、审核结果、来源冲突、是否占位、保存是否成功 | 工具从可信资料重建并强制执行 |
| 接受硬性时间调整或提示风险 | 用户通过独立确认入口明确授权 |
| 步数限制、请求键、版本控制字段、最终状态汇总 | 编排器；不由模型自行声称 |

保存与确认必须在统一写事务内再次检查资料、规则、逻辑时间及占用，避免“查询空闲、提交时已被占”的漏洞。待确认稿不占位，所以确认时冲突是正常可拒绝情形；不能因此自动迁移用户确认。已确认稿本版不可改期或撤销。

每次新保存调用由调度器分配请求键，故障重试保留原键原参。任务和素材组合的唯一约束进一步阻止换键重复建稿。历史重放返回当时响应，最终汇总查询当前草稿状态；原始硬性要求与风险始终保留。

采用来源/版本与可重建引用，避免模型提交假的审核布尔值。只读工具不写数据库缓存；确认入口不在模型工具集合内。没有到期业务，因此不引入草稿 TTL，也不在时间推进中发布。

详细字段、资料合并、四类工具、确认及迁移契约见 [06-business-contract.md](06-business-contract.md)。测试设计见 [07-acceptance-map.md](07-acceptance-map.md)。本阶段交付 JSON 资料，不运行 v1→v2 迁移、不新增业务 CLI 命令。

## 第三阶段实现

contracts.py 按操作校验 payload；原基础请求的规范化文本不变。runtime.py 继续负责统一校验、重放、事务和恢复；business.py 在同事务内读状态并生成 SQL 写入计划，draft_tools.py 强制草稿/确认边界。v2 在原三表基础上显式增加业务表和唯一索引；升级失败完整回滚。

material_tools.py 纯函数处理来源合并和测试规则，business.py 的只读工具在 SQLite 读快照中调用它。Draft.review_basis 同事务保存原资料、规则及检查快照，读取旧草稿可恢复原依据。模型不能提交状态或审核结论。

agent.py 接收 `Model.next_action(context)`，只允许 read_material/check_rules/query_slots/save_draft/finish，限制当前任务及素材。每次新写分配键、重试保留原键；调用前将完整请求写入并刷新 JSONL Trace。模型调用在事务外。结果依据实际工具返回组装，已确认草稿不会自动改期。

model.py 保留 Protocol 与明确标注的 OfflineMock。Mock 根据实际观察选择补查、查询、保存或停止，用于离线验证编排；它是固定规则测试适配器，不满足真实模型 ReAct 证明。bailian.py 新增真实 qwen-plus 原生工具调用适配器、HTTPS 边界和持久化预算，详见 08-bailian.md。

## 第四阶段预算与评估工程

budget.py 独立管理策略 v2，bailian.py 保留兼容导出。每次 HTTP 请求前用 SQLite BEGIN IMMEDIATE 预留 0.10 元，有效 usage 以整数微元按保守费率结算，未知调用继续占用预留；冲突结算和未来策略拒绝。10 元总授权不变，已有 calls 通过原子登记策略升级保留，不清空历史。

评估器独立场景业务库、共享预算库；模型选择动作，测试程序单独执行确认、日历变更和恢复。checkpoint 先保留输入/故障说明，再保留实际结果和 Trace；失败不删记录。运行时、辅助代码及合成 JSON 指纹在最终评估器的每例前后核验，变化停止。真实评估使用修复前较窄指纹范围，差异、原脚本快照与证据边界在 [第四阶段报告](09-phase4-evaluation.md) 明示。
