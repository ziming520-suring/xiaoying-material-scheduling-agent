## 开发方式

- Python、CLI、本地 SQLite；Python 具体版本根据本机环境核实。
- 此选择不代表真实模型供应商、具体依赖或完整业务契约已确定。

## 统一请求校验

- 所有写操作经过统一入口。
- 校验期间允许只读查询及诊断记录，不修改业务状态、重放记录或逻辑时间。
- 入口进行格式校验，并支持业务校验器；业务条件通过后才能写入。

## 统一重放处理

- 调用方提供 request_id，按操作类型与 request_id 识别请求，并绑定参数摘要。
- 相同键、相同参数的已成功请求返回原结果，不再次执行，也不重新进行时效性业务判断。
- 相同键、不同参数返回冲突错误。
- 成功结果持久化，校验失败不占键。
- 确认没有写入的临时失败允许使用原键重试。
- 防重复覆盖并发提交及程序重启。
- 业务写入与成功结果记录处于同一事务，防止业务已写入而重放记录缺失。
- 重新评估已改变的业务条件使用新请求键。

## 统一时间推进

- 使用带时区的显式逻辑时间，禁止倒退；当前时间大于等于到期时间时视为到期。
- 由独立写操作推进，同样经过校验和重放处理。
- 一次推进及其到期结算整体提交或整体回滚。
- 所有到期结算集中在统一处理入口，业务接口不自行结算。
- 第一版没有业务到期对象，不注册草稿过期、确认超时、占位释放等规则。
- 推进时间不改变草稿、审核结果或用户确认状态，不触发真实发布。
- 可以使用仅用于测试的到期对象，验证到期边界、只结算一次与失败回滚；不得将其称为已实现业务到期结算。
- 相同时间推进不产生额外业务效果；独立新请求增加成功重放记录，但不改变时钟版本或重复结算。

## 后续业务校验

- 新请求指定的发布时间已经过去时拒绝，要求用户提供新时间，不擅自改期。
- 已成功请求重放仍返回原结果。
- 新排期必须严格晚于当前逻辑时间；恰好等于当前时间也拒绝。此项属于后续业务校验，不代表已经实现业务接口。

## 基础接口契约（已确认）

### 1. 范围和实现选择

采用已经确认的 Python、CLI、SQLite。入口统一处理本地数据库写操作，不在数据库事务中调用模型或远程服务。本节仅描述基础接口；素材读取、审核、排期与保存草稿的设计见文末第二阶段及详细业务契约。

第一版只开放两个基础写操作：

| 操作名 | 职责 | 参数 |
|---|---|---|
| `system.initialize` | 显式初始化逻辑时钟与基础数据库结构 | `initial_time` |
| `clock.advance` | 推进逻辑时钟，通过集中入口处理到期对象 | `target_time` |

另提供一个只读 CLI 命令 `clock`，查询当前逻辑时间。它不需要重放键，不创建数据库或更新时间。

初始化是显式设置操作：先完成请求校验，再创建或初始化存储，不能在导入模块、解析请求或普通查询时偷偷创建数据库。校验失败不能创建文件。合法初始化若遇到存储失败，允许留下没有已提交业务状态的 SQLite 文件或内部辅助文件，不把文件存在视作初始化成功。

### 2. 写请求结构

所有基础写操作使用同一种 UTF-8 JSON 请求结构：

```json
{
  "schema_version": 1,
  "request_id": "advance-001",
  "operation": "clock.advance",
  "payload": {
    "target_time": "2026-10-28T18:00:00+08:00"
  }
}
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `schema_version` | 整数 | 必填，目前仅支持 `1`；布尔值不当作整数 |
| `request_id` | 字符串 | 必填，1–128 个 ASCII 字符，只允许字母、数字、点、下划线、连字符，区分大小写 |
| `operation` | 字符串 | 必填，当前只允许上表中的两个操作名 |
| `payload` | 对象 | 必填，字段由操作定义 |

拒绝未知字段、重复 JSON 键、错误类型、`null`、非标准 JSON 数值及不支持的版本。基础操作的 payload 只接受指定的一个时间字符串，没有隐式默认参数。

JSON 字段顺序不影响请求含义。输入不自动修剪空格、不修正拼写、不猜测日期，也不把字符串数字转成数值。

### 3. 时间格式与初始化

建议约定：

- 时间格式严格采用 `YYYY-MM-DDTHH:MM:SSZ` 或 `YYYY-MM-DDTHH:MM:SS±HH:MM`；必须有日期、秒与时区，不接受小数秒、无时区时间、闰秒或只有 `18:00` 的输入。
- 偏移量不超过 `±14:00`，小时与分钟必须合法；转换后必须在可表示日期范围内。
- 内部比较和存储统一转换成 UTC；对外统一返回以 `Z` 结尾的 UTC 时间，保留到秒。
- 省略时区时报错，不默认使用电脑所在时区；不静默舍入时间。
- 初始化时间由调用方通过 `initial_time` 明确给出，不读取电脑当前时间作为业务默认值。
- 初始化后使用不同请求键再次初始化，返回 `ALREADY_INITIALIZED`；同键同参重放返回原初始化结果，不重置时钟。
- `clock.advance` 的目标时间小于当前时间时返回 `TIME_REVERSED`；等于当前时间时成功但不再次执行到期处理；大于当前时间时才推进。
- 相同时间、不同请求键的合法操作可以保存各自的成功重放记录，但不增加时钟版本或产生到期效果。
- 已成功推进请求的重放返回当时的结果；即便时钟后来继续前进，也不改变旧结果。需要最新状态时调用只读查询。

后续业务的“发布时间已过去”必须拒绝；用户已确认发布时间恰好等于当前逻辑时间也拒绝，即新排期必须严格晚于当前时间。它与到期处理的 `due_at <= target_time` 是两个不同规则。

### 4. 成功与失败响应

统一响应字段必须全部出现，没有值的字段使用 `null`：

```json
{
  "schema_version": 1,
  "request_id": "advance-001",
  "operation": "clock.advance",
  "status": "succeeded",
  "data": {
    "previous_time": "2026-10-28T09:00:00Z",
    "current_time": "2026-10-28T10:00:00Z",
    "clock_version": 2,
    "settled_count": 0
  },
  "error": null
}
```

以上 JSON 仅用于说明格式，假定原时钟版本为 1，不是实际运行证据。

| 字段 | 类型 | 语义 |
|---|---|---|
| `schema_version` | 整数 | 响应契约版本，固定为 `1` |
| `request_id` | 字符串或 null | 已通过字段校验的请求 ID；无法可靠取得时为 null |
| `operation` | 字符串或 null | 已识别的操作；无法识别时为 null |
| `status` | 字符串枚举 | `succeeded`、`failed`、`unknown` |
| `data` | 对象或 null | 只有 succeeded 返回操作结果；其他情况为 null |
| `error` | 对象或 null | 只有 succeeded 为 null；其他情况包含错误信息 |

`failed` 表示本次调用没有提交新业务变更；不否认该键以前已经成功，例如同键不同参冲突不会删除以前的结果。`unknown` 表示无法确认本次是否已经提交，绝不能伪装成成功或确定失败。

错误对象字段：

| 字段 | 类型 | 语义 |
|---|---|---|
| `code` | 字符串 | 稳定错误码，见下表 |
| `message` | 字符串 | 面向用户的简短说明，不包含密钥、原始堆栈或敏感数据 |
| `field` | 字符串或 null | 相关字段路径，例如 `payload.target_time` |
| `retryable` | 布尔值 | 是否可以原键原参重试；不表示保证下一次成功 |

响应不设置动态 `replayed` 或当前真实时间字段，以保证重放返回原响应内容。是否命中重放由诊断 Trace 单独记录。

各操作的成功 data：

| 操作 | 字段 |
|---|---|
| `system.initialize` | `current_time: string`、`clock_version: int`；首次初始化版本为 1 |
| `clock.advance` | `previous_time: string`、`current_time: string`、`clock_version: int`、`settled_count: int` |
| 只读 `clock` | `current_time: string`、`clock_version: int`；统一响应中 request_id 为 null、operation 为 `clock.read` |

时钟严格前进时版本加 1；相同时间不加。第一版没有业务到期处理器，正常推进的 `settled_count` 为 0。

### 5. 错误码与退出码

| 错误码 | 含义 | 原键原参可重试 |
|---|---|---|
| `INVALID_REQUEST` | JSON、字段、类型、时间格式或范围非法 | 否 |
| `UNSUPPORTED_VERSION` | 不支持的请求版本 | 否 |
| `UNKNOWN_OPERATION` | 未注册的操作 | 否 |
| `IDEMPOTENCY_CONFLICT` | 同操作、同键对应的规范化参数不同 | 否 |
| `NOT_INITIALIZED` | 存储尚未初始化 | 否；先初始化 |
| `ALREADY_INITIALIZED` | 新请求试图再次初始化 | 否 |
| `TIME_REVERSED` | 新推进请求早于当前逻辑时间 | 否 |
| `STORAGE_BUSY` | 未提交，存储暂时忙或锁等待超时 | 是 |
| `STORAGE_ERROR` | 已确认没有提交的存储错误 | 是；应先解决存储故障 |
| `SETTLEMENT_FAILED` | 到期处理失败且整个事务已回滚 | 是；应先解决处理器故障 |
| `INTERNAL_ERROR` | 未预期错误，已确认没有提交 | 否；先排查实现 |
| `OUTCOME_UNKNOWN` | 无法确认提交结果 | 是，但必须保持原键原参，通过重放核对 |

成功退出码为 0，输入／规则拒绝为 2，存储或处理失败为 3，提交结果不确定为 4。`--help` 成功退出码为 0，不属于业务请求。

所有错误结果暂不持久化为成功重放记录。失败诊断可记录；修正校验错误后可以使用原来未占用的键，但已成功键不得改参数。

### 6. 重放身份与参数规范化

- 重放唯一键为 `(operation, request_id)`；本地单用户数据库内生效，不新增租户或用户权限模型。
- 摘要内容为 `schema_version`、`operation` 和经过操作校验的规范化 payload，不包含 request_id、数据库路径、日志路径或系统时间。
- 时间先转成 UTC 秒精度格式；同一时间的 `+08:00` 与 `Z` 写法视为相同参数。
- 对象键排序，UTF-8 编码，固定紧凑 JSON 序列化后计算 SHA-256；同时保存规范化请求文本用于核对。
- 同键同规范化请求返回存储的原成功响应；同键不同规范化请求返回冲突，不执行处理器。
- 第一版不设置重放记录 TTL，不自动清理；跨进程和重启后仍能识别已成功请求。
- 如果未来改变参数规范化语义，必须通过契约版本管理，不能让旧键被静默解释成新请求。

### 7. 最小持久化结构

数据库结构是实现建议，不是题面给定的表名。

| 表 | 字段与约束 |
|---|---|
| `runtime_meta` | `singleton_id INTEGER PRIMARY KEY CHECK(singleton_id = 1)`；`storage_schema_version INTEGER NOT NULL`，第一版为 1 |
| `logical_clock` | `singleton_id INTEGER PRIMARY KEY CHECK(singleton_id = 1)`；`current_time_utc TEXT NOT NULL`；`version INTEGER NOT NULL CHECK(version >= 1)` |
| `replay_results` | `operation TEXT NOT NULL`、`request_id TEXT NOT NULL`，组合主键；`request_digest TEXT NOT NULL`；`canonical_request_json TEXT NOT NULL`；`response_json TEXT NOT NULL` |

只保存已成功操作的完整响应；不提前写入“处理中”记录来占键。不建立素材表、草稿表或生产用到期任务表。

数据库必须完整初始化，不能仅凭文件存在判定可用；不支持的存储版本应明确报错，不能自动重建或覆盖已有文件。建议错误码 `STORAGE_ERROR`，并在 message 说明版本不兼容。

### 8. Python 内部接口

以下列出已实现的主要内部接口；精确类型和实现以 `project1/src/schedule_agent/` 为准：

```python
parse_and_validate(raw_json: str) -> ValidatedRequest
canonicalize(request: ValidatedRequest) -> CanonicalRequest
execute_write(request: ValidatedRequest, store: Store) -> Response
lookup_replay(tx: Transaction, request: CanonicalRequest) -> Response | None
validate_preconditions(tx: ReadOnlyTransaction, request: ValidatedRequest) -> None
initialize_clock(tx: Transaction, initial_time_utc: str) -> dict
advance_clock(tx: Transaction, target_time_utc: str) -> dict
settle_due(tx: Transaction, previous_time_utc: str, target_time_utc: str) -> int
read_clock(store: Store) -> Response
```

- `ValidatedRequest` 表示格式合法，不代表已经通过有状态的前置条件校验。
- `CanonicalRequest` 包含规范化请求、规范化 JSON 与摘要。
- `Store` 表示显式指定的本地 SQLite 存储，`Transaction` 表示当前事务上下文；处理函数不能自行提交、回滚或打开另一份数据库。
- `ReadOnlyTransaction` 仅提供查询能力；前置条件校验不得写数据或执行外部动作。
- 预期校验错误由统一入口转换为 Response，不能直接使 CLI 输出未处理的异常堆栈。
- 所有写处理器只能由 `execute_write` 调用；CLI 不直接绕过统一入口调用它们。
- `settle_due` 是唯一到期处理入口：未来处理器只能更新同一 SQLite 事务内的状态，不得在其中发消息、发布内容或调用不可回滚的外部服务。
- 第一版业务处理器列表为空；测试专用对象和处理器只存在于测试环境，不能通过生产 CLI 启用。

### 9. 执行与事务边界

此处只定义保证契约所需的顺序，详细实现计划另行编写：

1. 读取并解析请求，完成无状态格式校验和规范化；失败直接返回，不打开写事务、不创建数据库。
2. 对已有存储进入同一个 SQLite 写事务，通过串行化写入避免两个进程同时越过重放检查。初始化的建表也在受控事务内完成。
3. 检查重放键：同参命中则返回原成功结果；异参命中则报冲突。两种情况都不执行业务或推进时间。
4. 未命中时，只读校验当前状态和业务前置条件；失败回滚，不保存重放结果。取得锁或开启事务本身不等于修改业务状态。
5. 执行处理器。时间推进及到期结算在同一事务中完成。
6. 构造并序列化成功响应，将业务变更和成功重放记录一起提交。提交确认前不得输出成功。
7. 失败时回滚。提交结果不明确时，重新读取原键核对；查到匹配结果则返回原成功响应；无法核实时返回 `OUTCOME_UNKNOWN`，保留原键重试，不盲目换键重做。

建议 SQLite 锁等待上限为 5 秒，超时返回 `STORAGE_BUSY`，不在内部无限重试。该值是基础存储等待时间，不是后续 Agent 工具调用次数或执行步数上限。

### 10. CLI

模块名为 `schedule_agent`。在 `project1` 中设置 `PYTHONPATH=src` 并创建 `var` 目录后可运行以下命令；详细 PowerShell 命令见 `project1/README.md`：

```powershell
python -m schedule_agent run --db ./var/runtime.sqlite3 --input ./examples/initialize.json
python -m schedule_agent run --db ./var/runtime.sqlite3 --input ./examples/advance.json
python -m schedule_agent clock --db ./var/runtime.sqlite3
```

- `run` 必须显式提供 `--db` 与 `--input`；输入文件只能包含一个 JSON 对象。
- `clock` 必须显式提供 `--db`，使用只读方式打开已有数据库。
- 第一版不支持命令内批处理、隐式读取 stdin 或隐式创建目录。父目录不存在时明确报错。
- stdout 只输出一份 UTF-8 JSON 结果；诊断信息写入 stderr。Trace 的文件落盘方式在验证材料阶段补充，不把日志写入成功响应。
- 本机开发可用已核实的 Python 完整路径替代命令中的 `python`；正式交付再按项目布局给出安装步骤。

| B07 | 先推进至 T2，再重放先前推进至 T1 的成功请求 | 返回原 T1 结果，实际时钟仍为 T2，不报倒退、不再次执行 |
| B08 | 新键向过去推进 | TIME_REVERSED，时钟、处理对象和重放记录不变 |
| B09 | 写入后、提交前注入失败 | 全部回滚；修复故障后原键可成功执行一次 |
| B10 | 两个独立进程同时提交同键同参 | 只执行一次；等待完成者读取原结果，等待超时者明确返回 STORAGE_BUSY |
| B11 | 关闭进程并重新打开，提交已成功请求 | 返回持久化的原结果，没有重复效果 |
| B12 | 测试对象在 T 到期，先推进至 T 前再推进至 T | T 前不结算，T 时结算一次；后续推进不重复结算 |
| B13 | 测试到期处理器部分执行后抛错 | 对象变更、时间推进和重放记录全部回滚 |
| B14 | 提交成功但响应丢失，随后原键重试 | 查回原成功结果，不重复执行 |
| B15 | 提交结果不确定且暂时无法读取存储 | 返回 unknown / OUTCOME_UNKNOWN，不虚报成功或确定失败 |
| B16 | 第一版真实配置推进到未来 | settled_count 为 0；不发布、不自动确认、不修改草稿或审核结果 |

## 已确认的具体选择

1. 统一请求与响应字段、操作名、错误码及退出码是否采用本草案。
2. 时间由显式初始化给出，秒精度、必须带时区、统一返回 UTC；新排期必须严格晚于当前逻辑时间是否接受。
3. 只持久化成功结果、暂不设置重放过期清理；相同时间的新请求允许写入重放记录是否接受。
4. 锁等待 5 秒，以及无法确认提交时明确返回 unknown 的处理方式是否接受。

上述第 1–4 项已获用户“全部同意”。后续按本文执行，不重复索取确认。

## 第二阶段业务规则（用户已批准，设计与资料已落盘）

本节是本项目采用的设计，不冒充题面原文。字段、枚举、工具与错误契约以 [业务契约 v1](06-business-contract.md) 为准；输入和预期见 [合成资料](../data/README.md) 及 [验收映射](07-acceptance-map.md)。本节与基础层规则同时适用。

### 范围与正常路径

- 单账号、固定可选时段，每个时段最多一项素材。合成元数据与文案，不读取或识别真实图片、视频。
- 每项素材指定精确时间，全部视为硬性要求；保留原要求，不由模型静默修改。
- 无风险且原时段可用，直接保存已确认草稿并占位；依据是原始用户要求。“已确认”只代表草稿和占位成立，不代表已发布。
- 替代时段或提示风险只保存待确认稿，不占位；必须用户明确确认并重新检查后才占位。
- 批量逐项处理、逐项保存，保留成功项，逐项报告失败和缺口。待确认稿不算完成排期；全部完成为 completed，部分完成为 partial，无完成项为 incomplete。

### 资料、风险与确认

- 请求缺 material_id 是非法请求；素材存在但缺授权信息是业务资料不足，不混用错误类型。
- 素材与补充资料携带来源和版本。补充只能填缺失值，不能覆盖已知字段；基础/补充或补充之间矛盾必须报告并阻断。
- 草稿同事务保存不可变审核依据快照，包含原始素材、补充资料、有效内容、来源版本、规则和检查结果。当前资料更新后，已确认稿仍能恢复当时依据，不能只留摘要引用。
- 保留全部问题，审核主状态优先级：阻断 > 资料不足 > 需要确认 > 通过。
- 测试规则：标题/文案/授权缺失为资料不足；明确未授权、命中“保证收益”、来源冲突为阻断；人工复核标记为提示风险。它们不代表真实平台或法律规则。
- 用户确认绑定具体草稿版本、接受的时段及提示风险 ID。模型不能产生有效用户确认，阻断风险不能被确认豁免。
- 同任务同素材只有一份草稿。待确认建议更新原稿且版本递增；旧确认失效。已确认稿本版不支持自动改期、撤销或释放。

### 工具和基础层衔接

- 模型仅可调用素材读取、规则检查、时段查询、草稿保存；用户确认由独立 CLI 处理，不注册为模型工具。
- 工具只接受可重建的可信资料引用，不接受模型自报“审核通过”、占位或确认状态。
- 查询同时考虑已有排期与已确认草稿；待确认稿不占位。正常保存和确认占位必须在同一写事务内重新核验资料、规则、时段，防止查询后冲突。
- 写操作继续经过校验、重放、事务；单次失败不修改草稿、占位、确认记录或成功重放。模型调用在数据库事务之外。
- 技术重放与业务唯一性独立。已成功原键返回原结果；重新规划分配新调用键；换键仍不能生成第二份同任务同素材草稿。unknown 保留原键原参核对。
- 不新增草稿过期、不自动确认、不接真实发布。时间推进仍由基础层统一入口处理；新的占位必须严格在逻辑时间之后。
- 基础数据库升级将采用显式原子的 v1→v2 迁移，保留旧逻辑时间和重放记录，不静默重建；本阶段未执行迁移。
