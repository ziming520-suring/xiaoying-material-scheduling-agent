# 基础阶段复盘

本阶段最重要的问题是区分“确定失败”与“提交成功但响应丢失”。若把后者直接当作失败并换新键重做，就可能重复生效。当前通过状态和重放结果同事务提交，以及异常后的原键核对处理；无法核实时明确 unknown。

实际遇到的工程问题是 Windows 下数据库文件仍被占用。根因包括测试误以为 sqlite3 的上下文会关闭连接，以及生产连接建立后设置 PRAGMA 失败时未清理。修复针对连接生命周期，未通过忽略清理错误掩盖问题。

时间推进没有强行添加草稿过期规则。通过独立测试对象证明集中结算、到期边界与回滚，生产配置仍没有业务到期动作。这使题面边界与基础能力验证保持一致。

第二阶段已定义素材与规则数据、排期冲突范围、风险阻断和用户确认契约。下一步是第三阶段实现四类业务工具、独立确认入口、迁移与模型动作循环。新业务写操作必须继续复用当前基础入口，不得把固定条件分支伪装成模型决策。

第二阶段最需分清的是保存成功、确认成立、真实发布三个不同结果。待确认稿保存成功仍未完成排期；确认绑定具体版本与风险；系统完全不执行发布。另一个设计重点是保留模型选择空间：时段工具只提供实际候选，不强制选择最早时段；静态场景允许多个合法建议，不能把固定答案当作智能性证明。

实际投入时间：用户三天是可用窗口，不能视为连续开发时长；本仓库未运行完整人工计时器，因此目前不报告未经核实的总开发工时。测试执行耗时在 test-summary.json 中记录，不能作为项目总用时。

## 第三阶段补充

本地业务已实现，最容易漏的是“写时正确”不等于“最终显示正确”。用户可能在 Agent 处理另一项时确认先前草稿，最终结果必须重新读当前状态；并且最新建议不能再被旧查询缓存覆盖。另一个边界是日志失败：此前已提交的成功项必须继续明确报告，不能因为 Trace 无法写入就说整批失败。

通过失败测试及独立审查补齐了确认记录与占位的一致性检查、重放请求身份绑定、深层非法 JSON 和 Trace 失败边界。此后已接入百炼并进行了真实模型验证，结果独立记录，离线 Mock 的成功不能替代这一环节。

## 真实模型接入的学习与改进

最难的问题不是连通 API，而是让模型正确理解“工具调用成功”和“业务审核通过”不同。第一次把 observations 整体放进用户 JSON，模型在缺资料时重复读取并尝试保存。工具拒绝了保存，但这只能证明防线有效，不能算模型决策正确。改为原生 assistant/tool 历史并解释 review_status 后，模型开始依据缺口选择停止。

另一个问题来自上下文回传：模型当次输出的 reason 已被记录在 Trace，却没随历史动作送回模型，导致后续模型也省略必填 reason。增加只包含结构分类的错误诊断定位 missing_reason，再保留模型原本的简短依据，避免通过放宽校验或编造依据来掩盖问题。

真实模型可以在读到明确缺口后直接请求补充，不一定先运行规则检查。原汇总器隐含固定流程假设，未列出这一路径的缺失字段。现在根据可信读取结果列出缺口，不虚构未执行的规则检查。

下一阶段需以固定版本开展更完整的重复评估、提示风险及确认竞争验证、代码解释和交付检查。已有单次通过不等于稳定成功率；模型别名与服务行为可能变化，记录失败和版本比挑选成功截图更有价值。没有完整工时计时记录，不将测试运行耗时冒充开发用时。

## 第四阶段学习与下一步

上述重复评估现已完成：8 个核心场景各 3 轮全通过，全部真实 34 次中仍有 1 次无空位场景失败。模型看到 alternatives=[] 后尝试保存被占时段，工具拒绝；最后虽正确解释无法排期，仍应计入无效动作和状态预期失败。工具强约束与模型计划质量要分开评估，不能把安全拒绝一律写成成功。

预算最初把每次预留永久占用，实际估算约 0.163 元时却只剩 4 次调用。改为保留历史、有效用量按更高费率结算、未知调用不释放，既维持 10 元限制，也避免把预留当实付。实现采用整数微元、事务和重复结算校验，已有记录迁移前后逐行一致。

独立审查进一步发现：评估最后一例也必须检查版本变化；源代码冻结不等于数据冻结；故障说明必须在潜在失败之前保存。修复只涉及评估器时，应保存旧脚本和旧结果并说明范围，不能暗示真实评估已经用新验证器重跑。

下一阶段整理 GitHub 仓库与提交 SHA、复现入口、最终交卷清单；候选人需自行解释事务、确认、重放、模型行为与费用估算。后续模型优化优先无空位停止与存储故障辨别，用新场景复测而不是单例反复重试。实际总开发工时仍未完整记录。
